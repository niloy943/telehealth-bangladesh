1. EXECUTIVE SUMMARY
================================================================================
HealNSight has evolved from an initial prototype with simulated mock data into an
integrated, production-grade telemedicine ecosystem tailored to Bangladesh's 
healthcare infrastructure.

All core subsystems are fully functional and connected:
- A genuine OpenAI-powered conversational AI Health Assistant with Bangladesh 
  healthcare context and bilingual (Bengali/English) medical triage.
- A fully integrated, bank-grade SSLCommerz V4 payment gateway with hosted checkout,
  server-side Order Validation API checking, idempotency, and digital receipts.

2.2 PAYMENT GATEWAY ARCHITECTURE (SSLCOMMERZ LIVE & SANDBOX V4)
--------------------------------------------------------------------------------
* PREVIOUS STATE:
  Hardcoded sandbox URL, fake callback checking string equality, frontend asking 
  for credit card PIN and mobile number directly, only wired to medicine orders.

* CURRENT IMPLEMENTATION:
  - Production-Ready SSLCommerz Service Layer in `backend/api/payment_service.py`:
    * Official V4 API payload structure (store credentials, customer info, URLs).
    * Dynamic live vs sandbox host routing:
      Live Initiation:    `https://securepay.sslcommerz.com/gwprocess/v4/api.php`
      Live Validation:    `https://securepay.sslcommerz.com/validator/api/validationserverAPI.php`
      Sandbox Initiation: `https://sandbox.sslcommerz.com/gwprocess/v4/api.php`
      Sandbox Validation: `https://sandbox.sslcommerz.com/validator/api/validationserverAPI.php`
  - Strict Server-Side Order Validation:
    * Server queries the SSLCommerz Order Validation API (`validationserverAPI.php`) 
      directly server-to-server.
    * Enforces: status == 'VALID' / 'VALIDATED', exact `tran_id` match, currency == 'BDT', 
      and exact amount match within 0.01 BDT tolerance.
  - Server-Authoritative Fee Calculation (Anti-Tampering):
    * Completely ignores any client-supplied amount parameters.
    * Appointments: authoritatively queried from `DoctorProfile.fees` (default 500 BDT).
    * Pharmacy: authoritatively computed from medicine catalog prices + 50 BDT delivery.
    * Blocks duplicate payments for already paid appointments or confirmed orders.
  - Database Schema & Migration:
    * `Appointment`: added `payment_status` ('unpaid', 'pending', 'paid', 'refunded').
    * `PaymentTransaction`: added `user`, `currency`, `gateway`, `val_id`, `bank_tran_id`, 
      `card_type`, `card_brand`, `failure_reason`, `gateway_response`, `updated_at`.
    * Applied Database Migration: `0007_appointment_payment_status_and_more.py`.
  - Views & Endpoints:
    * `POST /api/payment/initiate/` -> Creates pending transaction, returns hosted checkout URL.
    * `POST/GET /api/payment/callback/` -> Validates transaction, updates state, redirects browser.
    * `POST /api/payment/ipn/` -> Asynchronous server-to-server webhook with idempotency.
    * `GET /api/payment/status/<ref>/` -> Authenticated endpoint returning verified status.
    * `GET /api/payment/history/` -> Filterable transaction ledger for patient.
  - Frontend UI/UX (`PatientDashboard.jsx`):
    * Eliminated fake PIN and phone input boxes.
    * SSLCommerz Hosted Checkout Modal with payment channel selector (bKash, Nagad, Visa, etc.).
    * Security notice: 256-Bit SSL Encryption, notice that card credentials are never stored.
    * Callback listener reading return URL params, clearing query string, and verifying backend.
    * Payment Status Modal (Loading spinner -> Verified Checkmark / Failure reason).
    * Digital Printable Receipt Voucher with validation ID, bank reference, and print action.
    * "Billing & Payments" ledger subview with filter tabs (All, Completed, Pending, Failed).
  - Verification:

2.3 AUTHENTICATION, AUTHORIZATION & MULTI-FACTOR AUTHENTICATION (MFA)
--------------------------------------------------------------------------------
* CURRENT IMPLEMENTATION:
  - Role-Based Access Control (RBAC):
    * Three distinct roles: `patient`, `doctor`, and `admin` with strict permission classes.
  - Dual Authentication Architecture:
    * Django REST Framework using SimpleJWT (`/api/login/`, `/api/register/`).
    * Node.js Authentication Microservice (`http://localhost:5000/api/auth`) with 
      bcrypt password hashing and token generation.
  - Multi-Factor Authentication (MFA):
    * Database Model `OTPCode` in Django storing 6-digit numeric OTPs, expiry (5 min), 
      and usage state.
    * `SecureLoginView`: Prompts for credentials; if MFA is active, issues OTP and returns 
      `mfa_required: true`.
    * `MFAVerifyView`: Validates OTP code, marks it used, and grants full JWT token pair.
    * Brute-Force Rate Limiting: `LoginAttempt` tracks failed  and locks accounts 
      after repeated failures.
  - User Dashboards:
    * Distinct dashboards and navigation states for Patient, Doctor, and Administrator.

3.2 PRIORITY 2 (HIGH): WEBRTC TURN RELAY SERVER FOR CELLULAR NAT TRAVERSAL
--------------------------------------------------------------------------------
* CURRENT STATE:
  WebRTC in `ClinicalRoom.jsx` uses public Google STUN servers:
  `{ urls: 'stun:stun.l.google.com:19302' }`.
* THE ISSUE:
  STUN works well when both users are on broadband/open Wi-Fi. However, Bangladesh mobile 
  operators (Grameenphone, Banglalink, Robi, Airtel) use Carrier-Grade NAT (CGNAT) and 
  symmetric NAT. P2P WebRTC media connections between two mobile phones will fail to 
  negotiate ICE candidates without a TURN relay server.
* WHAT HAS TO BE FIXED:
  1. Deploy an open-source Coturn server on a cheap VPS (or subscribe to Twilio Network 
     Traversal / Xirsys).
  2. In `ClinicalRoom.jsx`, configure the `iceServers` array:
     ```javascript
     iceServers: [
       { urls: 'stun:stun.l.google.com:19302' },
       {
         urls: 'turn:turn.healnsight.com.bd:3478',
         username: 'turn_user',
         credential: 'turn_secure_password'
       }
     ]
     ```

--------------------------------------------------------------------------------
3.3 PRIORITY 3 (HIGH): PRODUCTION DATABASE MIGRATION (SQLITE -> POSTGRESQL)
--------------------------------------------------------------------------------
* CURRENT STATE:
  The Django backend and Node.js backend currently read and write to local SQLite 
  files (`backend/db.sqlite3`).
* THE ISSUE:
  SQLite locks the entire database file during write operations. Under concurrent live 
  traffic (multiple patients booking appointments and paying simultaneously), SQLite 
  will throw `sqlite3.OperationalError: database is locked`.
* WHAT HAS TO BE FIXED:
  1. Install `psycopg2-binary` in `backend/requirements.txt`.
  2. In `backend/telehealth_project/settings.py`, configure PostgreSQL:
     ```python
     DATABASES = {
         'default': {
             'ENGINE': 'django.db.backends.postgresql',
             'NAME': os.getenv('DB_NAME', 'healnsight_db'),
             'USER': os.getenv('DB_USER', 'postgres'),
             'PASSWORD': os.getenv('DB_PASSWORD', ''),
             'HOST': os.getenv('DB_HOST', 'localhost'),
             'PORT': os.getenv('DB_PORT', '5432'),
         }
     }
     ```
  3. Deploy a managed PostgreSQL instance on AWS RDS, Supabase, or DigitalOcean.

3.4 PRIORITY 4 (MEDIUM): LOCAL BANGLADESH SMS GATEWAY INTEGRATION FOR REAL OTPS
--------------------------------------------------------------------------------
* CURRENT STATE:
  Multi-Factor Authentication (MFA) generates real 6-digit cryptographic OTPs in the 
  database, but delivery is simulated in server logs or mapped through international 
  Twilio SMS.
* THE ISSUE:
  International SMS to Bangladesh numbers (+88017..., +88018..., +88019...) via Twilio 
  suffers from high per-SMS costs (approx. $0.06/SMS) and carrier filtering by BTRC.
* WHAT HAS TO BE FIXED:
  1. Integrate a local Bangladesh SMS aggregator:
     - SSL Wireless SMS API (`https://smsplus.sslwireless.com`) OR
     - Greenweb SMS Gateway OR
     - BulkSMSBD
  2. Implement an SMS adapter in `backend/api/sms_service.py` to dispatch OTPs via local 
     telecom alphanumeric sender IDs.
