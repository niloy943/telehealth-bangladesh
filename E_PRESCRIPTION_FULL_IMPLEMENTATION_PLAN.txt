1. EXECUTIVE SUMMARY & ARCHITECTURAL OBJECTIVES
================================================================================
The HealNSight Secure E-Prescription System is designed to replace traditional,
insecure digital prescription handling (such as plaintext PDF downloads, static 
links, and unencrypted databases) with a cryptographically enforced, tamper-
evident, and zero-trust clinical architecture.

KEY OBJECTIVES ACHIEVED:
1. Envelope Authenticated Encryption: Every medical prescription is encrypted 
   at rest using a unique 256-bit Data Encryption Key (DEK) operating in 
   Galois/Counter Mode (AES-256-GCM). DEKs are wrapped using Master Key Encryption 
   Keys (KEKs) via Cloud Key Management Service (KMS).
2. Tamper-Evident Blockchain Ledger: Document integrity is permanently anchored 
   to a private Hyperledger Fabric blockchain. Zero Protected Health Information 
   (PHI) is written to the ledger; only immutable SHA-256 Merkle hashes, version 
   identifiers, and transaction IDs are committed.
3. Strict Consultation Grant Enforcer: Doctors receive temporary, time-bounded 
   grants (ConsultationGrant) to view vitals, allergies, and patient records. 
   Upon digital signing and approval, the doctor's grant is irreversibly revoked. 
   Under medical privacy regulations, doctors cannot inspect finalized records.
4. Guaranteed Post-Consultation Patient Access: Revocation of the consultation 
   session does not block the authenticated patient. The document owner retains 
   permanent access to view and download finalized prescriptions through the 
   Patient E-Prescription Portal, with on-the-fly blockchain verification.
5. Google Authenticator (RFC 6238 TOTP) Mandatory 2FA: High-security actions 
   (signing prescriptions and unlocking security locks) require entering 
   a rotating 6-digit TOTP code paired with the user's mobile authenticator.
6. Zero-Popup In-Call Consultation Workspace: The legacy multi-window modal 
   experience and floating external portals have been completely eliminated. 
   Prescription formulation occurs directly inside the active video/audio room, 
   preserving patient eye contact and clinical flow.

3. CRYPTOGRAPHIC SECURITY BLUEPRINT (AES-256-GCM ENVELOPE ENCRYPTION)
================================================================================
All clinical prescriptions exist in encrypted form at rest and in transit.

1. DATA ENCRYPTION KEY (DEK) GENERATION:
   - For every prescription generation event, the crypto engine generates:
     * DEK: crypto.randomBytes(32) -> 256-bit cryptographic key
     * IV:  crypto.randomBytes(12) -> 96-bit initialization vector
   - No two documents share the same DEK or IV.

2. GALOIS/COUNTER MODE (GCM) AUTHENTICATED ENCRYPTION:
   - Cipher: aes-256-gcm
   - Produces ciphertext and a 16-byte authentication tag (authTag).
   - Tamper Detection: Changing even a single bit of ciphertext invalidates 
     the authTag during deciphering, causing Node.js crypto to reject the 
     operation with ERR_CRYPTO_OPERATION_FAILED.

3. KEY ENCRYPTION KEY (KEK) & CLOUD KMS WRAPPING:
   - Plaintext DEKs are never written to disk, database records, or log files.
   - The DEK is wrapped using the platform Master KEK via AES-256-CBC/KMS.
   - The database stores: { wrappedKey, iv, authTag, ciphertextPath, sha256Hash }.

4. DECRYPTION & ZERO-KNOWLEDGE STREAMING:
   - When the authenticated patient requests their prescription:
     a) Backend fetches the wrapped DEK and unwraps it in volatile RAM.
     b) Decipher stream decrypts ciphertext into transient buffer.
     c) Server streams binary application/pdf with Content-Disposition headers.
     d) Plaintext buffer is instantly released from RAM via garbage collection.

4. IDENTITY, GOOGLE AUTHENTICATOR 2FA & BMDC DIGITAL SIGNATURES
================================================================================
Prescriptions carry legal authority and can trigger life-critical medication 
dispensation. Simple password or checkbox authorization is strictly prohibited.

1. RFC 6238 TOTP ENGINE SPECIFICATION:
   - Algorithm: HMAC-SHA1
   - Token Length: 6 decimal digits (e.g. 354416)
   - Time Step Window: 30 seconds
   - Allowed Clock Drift: +/- 1 step (permitting slight client clock variance)
   - Source Module: totp.service.ts

2. PAIRING & ACTIVATION WORKFLOW:
   - Endpoint: POST /api/auth/mfa/setup
   - Generates 32-character Base32 secret (crypto.randomBytes(20)).
   - Generates otpauth:// URI containing issuer ("HealNSight") and user email.
   - Emits QR Code data URL for immediate scanning via Google Authenticator app.
   - Emits 8 single-use emergency backup recovery codes (TB-XXXX-XXXX).
   - Requires verification of first rotating token before enabling 2FA on account.

3. DOCTOR DIGITAL SIGNATURE AT PRESCRIPTION APPROVAL:
   - Endpoint: POST /api/prescriptions/approve
   - Payload: { consultationId, patientId, symptoms, diagnosis, medicines, totpCode }
   - The gateway validates that totpCode matches the authenticated doctor's secret.
   - Enforces Anti-Replay: Tracked token cache rejects reuse of the identical 
     6-digit code inside the active 30-second window.
   - Inscribes doctor's BMDC registration number and digital signature metadata.

4. EMERGENCY BACKUP RECOVERY CODES:
   - Generates 8 single-use cryptographically hashed backup codes.
   - Verifying an emergency code immediately marks it invalid, preventing reuse.

5. HYPERLEDGER FABRIC BLOCKCHAIN MERKLE LEDGER & ZERO-PHI POLICY
================================================================================
To guarantee non-repudiation and prevent retroactive tampering by malicious 
insiders or compromised databases, every prescription is anchored to blockchain.

1. ZERO-PHI ON-CHAIN ARCHITECTURE:
   - Under international healthcare regulations (HIPAA, GDPR) and Bangladesh 
     patient data protection directives, patient medical information must never 
     be recorded in permanent distributed ledgers.
   - The Hyperledger Fabric chaincode stores exclusively:
     {
       "docId": "rx-1793988977237-baptqpt",
       "version": "1.0",
       "sha256": "6c0cf05ff77d42e143560f8ee4d1d1d10a37b16fa5488bad62d16a7b74dad9b5",
       "timestamp": "2026-11-06T18:16:17.237Z",
       "txId": "tx_fabric_72782d31373933393838393737323337"
     }

2. CHAINCODE METHODOLOGY (prescription_integrity.js):
   - registerPrescriptionHash(stub, docId, version, sha256Hash)
     Validates arguments, constructs state object, and invokes stub.putState().
   - verifyPrescriptionHash(stub, docId, version, expectedHash)
     Fetches state from Merkle tree and performs strict string comparison.

3. PRE-DELIVERY FORENSIC VERIFICATION:
   - Before any PDF byte is transmitted to a requesting patient:
     a) Crypto engine reads encrypted ciphertext from storage.
     b) Computes crypto.createHash('sha256').update(ciphertext).digest('hex').
     c) Queries Hyperledger Fabric for the recorded sha256 digest.
     d) If digests match -> Proceed to decryption and streaming.
     e) If digests mismatch -> Trigger Forensic Quarantine (see Section 8).

6. CONSULTATION ACCESS CONTROL & LIFECYCLE MANAGEMENT
================================================================================
Patient privacy is governed by the ConsultationGrant state machine.

1. GRANT LIFECYCLE:
   - SCHEDULED: Patient books consultation. No doctor clinical grant active.
   - ACTIVE: Consultation begins (video or audio). Server issues a 60-minute 
     ConsultationGrant linked to the doctor, patient, and consultation session.
   - REVOKED: Triggered automatically upon:
     * Doctor digitally signing and approving the E-Prescription.
     * Consultation conclusion / termination.
     * 60-minute grant expiration.

2. IMMEDIATE POST-APPROVAL REVOCATION:
   - The instant POST /api/prescriptions/approve executes successfully:
     * prisma.consultationGrant.update({ where: { id }, data: { revokedAt: new Date() } })
     * Doctor's read access to patient allergies, vitals, and records is cut off.
     * Doctor attempting to download the finalized PDF receives 403 Forbidden.

7. POST-CONSULTATION PATIENT PDF ACCESS, PERSISTENCE & VERIFICATION
================================================================================
Addressing the post-consultation access invariant:

1. ARCHITECTURAL INVARIANT:
   - The revocation of the doctor's ConsultationGrant applies strictly to 
     the physician and unauthorized third parties.
   - It MUST NOT block the patient from retrieving their own prescription.

2. PERSISTENCE LAYER:
   - Encrypted ciphertext and metadata are stored persistently in:
     * SQLite/PostgreSQL: prescriptions and prescription_files tables.
     * Disk storage: telemedicine/data/storage/prescriptions/:id.enc
   - Retains ciphertext permanently across server reboots.

3. PATIENT OWNERSHIP VERIFICATION PIPELINE:
   - Endpoint: GET /api/patient/prescriptions/:id/download
   - Headers: X-Patient-ID: <authenticated_patient_id>
   - Backend Verification Sequence:
     1. Retrieve prescription from persistent database.
     2. Authenticate patient identity.
     3. Verify prescription.patientId === authenticatedPatientId.
        If mismatch -> Return 403 Forbidden ("Unauthorized Access").
     4. Check DocumentLock status:
        If locked -> Return 423 Locked ("Dual-Mode Recovery Required").
        If quarantined -> Return 403 Forbidden ("Document Quarantined").
     5. Read persisted ciphertext and compute SHA-256 hash.
     6. Compare hash against Hyperledger Fabric blockchain ledger.
        If mismatch -> Move to QUARANTINED, write audit alert, halt delivery.
     7. Unwrap DEK with Master KEK and decrypt ciphertext via AES-256-GCM.
     8. Stream application/pdf binary bytes directly to patient (HTTP 200).

4. PATIENT VAULT LISTING:
   - Endpoint: GET /api/prescriptions/patient/list
   - Returns all historical approved prescriptions for the patient, populated 
     with diagnosis, doctor BMDC info, and blockchain verification pills.

8. THREAT DETECTION, BURST LOCKDOWN & DUAL-MODE RECOVERY
================================================================================
The security lockdown service (security-lockdown.service.ts) detects automated 
attacks, brute-force attempts, and credential abuse.

1. AUTOMATED LOCKDOWN TRIGGERS:
   - Brute-Force Burst: Exceeding 5 failed download or auth attempts in 60 seconds.
   - Grant Bypass: Attempting to call clinical APIs after grant revocation.
   - Identity Spoofing: Querying documents with a mismatched patient ID.
   - Blockchain Integrity Failure: Ciphertext hash mismatch against Fabric.

2. FORENSIC QUARANTINE (INTEGRITY FAILURE):
   - When a hash mismatch occurs:
     * Document status is immediately set to QUARANTINED.
     * An immutable SecurityEvent alert is logged.
     * All access is permanently halted.
     * OTP and TOTP unlocking is strictly blocked; requires forensic audit.

3. DUAL-MODE PATIENT IDENTITY RECOVERY (FOR RECOVERABLE LOCKS):
   When access is locked due to bursts, the patient can restore access via:
   
   MODE A: GOOGLE AUTHENTICATOR (INSTANT TOTP)
     - Endpoint: POST /api/security/prescriptions/:id/verify-totp
     - Payload: { totpCode: "123456" }
     - Validates rotating 6-digit TOTP against patient's paired 2FA secret.
     - Unlocks document immediately upon validation.

   MODE B: SINGLE-USE 5-MINUTE OTP CHALLENGE (FALLBACK)
     - Request Endpoint: POST /api/security/prescriptions/:id/request-otp
     - Dispatches 6-digit cryptographic challenge to patient email/SMS.
     - OTP is hashed using bcrypt and stored with a 5-minute TTL.
     - Verify Endpoint: POST /api/security/prescriptions/:id/verify-otp
     - Payload: { otpCode: "654321" }
     - Validates challenge, enforces max 3 attempts, marks OTP consumed, 
       and restores document access to ACTIVE.

10. COMPLETE DATABASE SCHEMA & STATE MACHINES (10 CORE ENTITIES)
================================================================================
The relational data model consists of 10 primary entities:

1. User
   - id, email, passwordHash, role ('doctor'|'patient'|'admin'), bmdcNumber,
     mfaSecret (Base32), mfaEnabled, backupCodes (JSON array), createdAt.
2. Consultation
   - id, patientId, doctorId, type ('video'|'audio'), roomName, 
     status ('SCHEDULED'|'ACTIVE'|'COMPLETED'|'CANCELLED'), startedAt, endedAt.
3. ConsultationGrant
   - id, consultationId, doctorId, patientId, expiresAt, revokedAt, createdAt.
4. Prescription
   - id, consultationId, doctorId, patientId, chiefComplaints, clinicalDiagnosis,
     doctorAdvice, version, status ('DRAFT'|'APPROVED'|'GENERATING'|'READY'),
     securityStatus ('ACTIVE'|'LOCKED'|'QUARANTINED'), approvedAt.
5. PrescriptionItem
   - id, prescriptionId, medicineName, dosage, frequency, duration, instructions.
6. PrescriptionFile
   - id, prescriptionId, storagePath, wrappedKey, iv, authTag, sha256Hash,
     fileSizeBytes, createdAt.
7. SecurityEvent
   - id, eventType ('BURST_DETECTED'|'GRANT_BYPASS'|'INTEGRITY_FAIL'|'LOCKED'),
     targetResource, ipAddress, userAgent, details, timestamp.
8. DocumentLock
   - id, prescriptionId, reason, isForensicHold, lockedAt, unlockedAt.
9. OtpChallenge
   - id, prescriptionId, hashedOtp, expiresAt, attempts, consumed, createdAt.
10. AuditLog
   - id, userId, action, resource, ipAddress, status, timestamp.

STATE MACHINE LIFECYCLE:
[ DRAFT ] 
    |
    v (Doctor approval with valid Google Authenticator 2FA)
[ APPROVED ]  --> [ Doctor ConsultationGrant Instantly Revoked ]
    |
    v (Puppeteer rendering + AES-256-GCM + Fabric anchor)
[ READY ] 
    |
    +---> [ Suspicious Burst ] ---------> [ LOCKED ]
    |                                        |
    |                                        v (Google 2FA / 5-min OTP)
    |                                     [ READY ]
    |
    +---> [ Hash Mismatch vs Fabric ] ---> [ QUARANTINED ] (Forensic Hold)
